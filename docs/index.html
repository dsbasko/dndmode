macOS 14+ · Apple Silicon · foreground CLI

Lock your unattended MacBook without killing the work it is doing.

One command covers every display with a full-screen shield, blocks the keyboard and trackpad at the HID level, keeps the Mac awake and silences it — while the long job you left running never notices.

No daemon, no launchd, no menu-bar icon. You run it, you watch it, you end it.

The problem

You have to leave. The job cannot.

An AI agent is running in YOLO mode, or a build, or a render. You need to walk away from the laptop for two hours. Until now there were two options, and both cost you something.

Option A

Lock the screen

Ctrl+Cmd+Q is safe. But macOS may suspend or throttle the session behind the lock, and a black login screen is an invitation to walk away and forget the job is even alive.

May cost you the work.

Option B

Leave it open

The job keeps running at full speed. So does anyone who walks past: a keypress, a click on a confirmation dialog, a read of whatever is on screen. Your terminal is a public terminal now.

Costs you the machine.

Option C

dndmode

The job runs untouched at full speed, and the machine is covered on every display and inert to keyboard and trackpad until you come back and type your unlock code. Everything is exactly where you left it.

Costs you nothing but the typing.

dndmode is a soft-lock for cooperative spaces — home, an office, a coworking desk. It is not hardware-grade protection, and the threat model says so in detail rather than hiding it.

dndmode vs the alternatives

caffeinate does one of the five jobs.

caffeinate keeps the Mac from falling asleep. That is all it does — and it is genuinely all it claims. The screen stays lit, unlocked and fully interactive for anyone who walks past it.

There is a mode where dndmode is just caffeinate.

Run dndmode --style none and you get awake-only mode: no overlay, no input blocking, no mute, no Focus, and no Accessibility permission required. Under the hood that mode literally shells out to caffeinate, tying the assertion to dndmode's own pid so it self-releases even after a hard kill.

So the honest framing is not “better than caffeinate”. It is: staying awake is one of five jobs. dndmode normally does that one itself with an IOKit power assertion, and the other four are jobs caffeinate was never meant to do.

How it works

Four layers, and a fifth one underneath them.

Every layer is a documented macOS API doing exactly one job. The interesting one is the input lock, because the way it recognises your unlock code is also the reason a wrong code is indistinguishable from silence.

Input path — matching happens after interception, never inside it

  1. Keyboard · Trackpad

    15 event types, including media keys.

  2. CGEventTapCreate

    kCGHIDEventTap, head-inserted, suppression-capable.

  3. return NULL → WindowServer never sees the event

  4. 64-entry ring buffer

    A copy of (flags, keycode) only. Zero Go calls in the C callback; autorepeat dropped.

  5. Go matcher, every 10 ms

    Is the tail of what was typed equal to the unlock code?

  6. session ends — shield down, exit 0

No event ever passes the filter — not even the keys of your own unlock code. Because the match is computed after the fact rather than in the interception path, there is no “correct key” that behaves differently from a wrong one, and no keystroke ever surfaces in the app underneath.

Layer 1

Shield overlay

One borderless NSWindow per attached display, drawn above the screen saver. That places the shield over the menu bar, Dock, Mission Control, Spotlight, Cmd+Tab and the Force Quit dialog, on every Space and next to full-screen apps. Plugging a display, changing resolution or rearranging monitors rebuilds the overlay within 250 ms. The system cursor is hidden.

Layer 2

Input lock

Two event taps, both head-inserted and suppression-capable rather than listen-only. The primary one sits at the HID level and drops everything. A second tap at the session level swallows the gesture stream WindowServer synthesises past the HID point, so three- and four-finger swipes and the Launchpad pinch die before the Dock sees them. A watchdog probes every 5 s and re-enables both taps if macOS silently disabled them; after five failed attempts it ends the session with its own exit code, and an NSWorkspace observer re-arms them after sleep or fast user switching.

Layer 3

Awake lock

One IOKit power assertion named dndmode active, visible in pmset -g assertions so you can always see who is holding the machine up. By default it keeps the display lit as well; flip allow_display_sleep and the panel is allowed to idle off while the system keeps running.

Layer 4

Silence

System audio is muted for the session and restored on exit. The mute is state-aware: it records whether audio was already muted before the session and never unmutes what it did not mute. Notification banners never show because the shield sits above Notification Center. Do Not Disturb is a separate opt-in, off by default — macOS syncs Focus to your iPhone over iCloud, and there is no API to enable it on this device only.

Underneath

Crash safety

A snapshot records the pid, the assertion id and the prior audio and Focus state. A second instance detects the first and refuses to start. If a session is killed with kill -9, the next launch reads the snapshot, releases the orphaned power assertion by its exact id, conditionally restores audio and Focus, and deletes the file — so a hard kill never leaves the Mac stuck awake or muted.

The unlock code

Not a hotkey. A passphrase you type into a dead keyboard.

dndmode watches the tail of everything you type and ends the session the moment that tail equals your code. No prompt, no progress indicator, no wrong-code feedback, and no way to reset a half-typed attempt — you just keep typing until it matches.

Grammar

Steps are separated by spaces; each step is (<mod>+)*<key>. Modifiers inside a step are optional, so both s and ctrl+s are valid steps. A literal space is only a separator — the space key is written space.

Unlock-code grammar: modifiers and keys
Modifiers (case-insensitive, optional per step)ctrl   option   cmd   shift
Keysa-z   0-9   f1-f12   space   return (enter)   tab   escape (esc)   delete   forwarddelete   left   right   up   down   - = [ ] ; ' , . / \ `

Examples

unlock_code: s w o r d f i s h  # a passphrase — recommended
unlock_code: ctrl+s w o r d cmd+z  # mixed
unlock_code: Ctrl+Option+Cmd+X  # one chord = length 1
unlock_code: "- a b c d"  # leading punctuation: quote it

The value is a YAML scalar. If the code starts with - [ ] ' or `, wrap it in double quotes — unquoted, YAML parses those as list or quote syntax and startup dies with a YAML error rather than a dndmode one. A space followed by # always starts a YAML comment and would silently cut the code short.

Length is the whole security argument

alphabet ~36 · automated typist at 100 keypresses/second

Every keypress is a fresh match attempt. There is no lockout and no rate limit — that is a deliberate trade for silence, and it means short codes fall fast.

The bars plot the column beside them on a base-10 log scale, from five minutes at the left edge to three centuries at the right; the paler extension on the last two rows is the span between that band's two figures. Codes longer than 32 steps are rejected. A 1-step code without modifiers is rejected too — a bare key would unlock on the first thing a bystander types. The shipped default Ctrl+Option+Cmd+X is exactly the weak shape that motivated unlock codes; change it before you rely on it.

Three things that will trip you up

01

Physical positions, not characters

The code is matched by key position, so it behaves identically on US, Russian or AZERTY layouts. That also means s w o r d is typed on a Russian layout with the keys ы ц о р в. Pick your code by where your fingers go, not by what appears on screen.

02

A stray modifier breaks a step

Each step is matched exactly. A step written without modifiers matches only a press with no modifiers held, so resting on Cmd or Shift silently breaks it and the tail resets. Write the modifier into the step (cmd+s) if you intend to hold it.

03

Holding a key does not help

Auto-repeat presses are dropped before they reach the matcher, so a held key contributes exactly one step and cannot be used to sweep the code space. Genuine double letters are unaffected — auto-repeat only engages well past the speed of a real double tap.

Caps Lock, the numeric-keypad flag, the Fn flag and the other system-set modifier bits are stripped before matching, so a stray Caps Lock can never lock you out, the arrows and forwarddelete work as plain steps, and fn inside a step parses but means nothing.

Do not put f1–f12 in your unlock code

Stripping the Fn bit is not enough for the F-row. On the macOS default — “Use F1, F2, etc. keys as standard function keys” turned off — the F-row is not a key press at all: it is delivered as a system media event, which dndmode blocks but never records. A code containing f1 parses, validates and starts without a single warning, and then cannot be typed. Get it wrong and the screen stays locked with no keyboard and no Ctrl-C — the way out is SSH from another machine or a hard power-off.

Install

Pick one install path and stay on it.

All three paths build from source — there is no pre-signed bottle, the binary is ad-hoc signed locally, and none of them needs an Apple Developer ID.

Homebrew

easiest
$ brew install dsbasko/tap/dndmode
$ brew upgrade dndmode

From the personal tap dsbasko/homebrew-tap, not homebrew-core. Each upgrade rebuilds with a fresh cdhash, so macOS re-prompts for permissions afterwards.

Lands in /opt/homebrew/bin

From source

stable grants
$ git clone github.com/dsbasko/dndmode
$ cd dndmode
$ make install

Builds with the ad-hoc identifier com.dsbasko.dndmode. That identifier and its cdhash are stable across rebuilds, so a later git pull && make install keeps your permission grants.

Lands in /usr/local/bin

go install

quick
$ go install github.com/dsbasko/dndmode@latest

Every @latest rebuild changes the cdhash, so TCC sees a new app and re-prompts for Accessibility and Input Monitoring on each upgrade.

Lands in $(go env GOPATH)/bin

Mixing them produces separate binaries with different code signatures, and macOS TCC treats each as a different app — each needs its own Accessibility and Input Monitoring grant. If /usr/local/bin is not ahead of ~/go/bin in your $PATH, you may be granting permissions to one binary and running another.

First-run setup

The config file does not exist until dndmode runs. dndmode --help only prints usage and creates nothing.

01

Install dndmode by one of the paths above.

02

Run dndmode. The first launch writes the default config to ~/.config/dndmode/config.yml, then prompts for Accessibility. Click Open System Settings and enable dndmode under Privacy & Security → Accessibility.

03

It then waits for Input Monitoring. There is no system prompt for this one — dndmode opens the pane, and the run continues once you flip the switch.

04

Only if you want Focus/DND. In the Shortcuts app create two shortcuts: Set Focus → Do Not Disturb → Turn On Until Turned Off, saved as dndmode-on; and a second that turns it off, saved as dndmode-off. With the default focus: false you can skip this entirely.

05

Run dndmode again. With --debug you will see dndmode: active. press Ctrl-C. — and then change your unlock code before you rely on it: edit unlock_code, or run dndmode --set-password and type the new one at the prompt, which stores it hashed instead of in plaintext.

CLI reference

Every flag is per-run. The tri-state ones fall back to the config file.

No session flag writes to the config file, and there is no config key for --timer. A run is described entirely by the file plus the flags you typed for it. The one exception is --set-password, which starts no session at all: it rewrites a single key and exits.

Start

Run dndmode. It runs in the foreground and blocks the terminal until the session ends.

End

Type the unlock code, press Ctrl-C in the launching terminal, send SIGTERM/SIGHUP, or let --timer expire.

Report

Nothing on stdout or stderr. The outcome comes back as an exit code, and only --debug un-silences it.

Quiet by default is a security decision, not laziness

With glass or none the terminal stays visible while dndmode runs, and a printed startup banner would leak your unlock code to anyone watching over your shoulder. So dndmode prints nothing at all and reports outcome only through its exit code.

Even under --debug the banner confirms only that a code resolved and which config key it came from — never the code itself, and never its length, because the length is part of the secret. Both facts land on the same line, so source= and config= are read together.

$ dndmode
$ (nothing at all)
$ dndmode --debug
dndmode: unlock_code=ok (source=unlock_code) config=~/.config/dndmode/config.yml
dndmode: active. press Ctrl-C.

Nothing per-keystroke is ever logged either — not progress, not a failed match, not a count of dropped events. The length and timing of the secret are part of the secret.

Configuration

One file. One required key. Everything else is a commented default.

The config lives at ~/.config/dndmode/config.yml and is created on first run. Only unlock_code is written as an active key — or the unlock_salt / unlock_hash pair once --set-password has replaced it; every other setting ships commented at its default, so uncommenting a line only ever overrides.

Migrating from hotkey

Migration is a rename, with one caveat: spaces separate steps in unlock_code, so any spaces around the + have to go first. hotkey: Ctrl + X is a legal chord but reads as three steps and fails with exit 1.

fn is no longer a modifier: ctrl+fn+x now unlocks on Ctrl+X, and fn+x is a startup error because no modifier is left.

Or skip the editing: dndmode --set-password deletes the hotkey line along with unlock_code and writes a salted hash where it was, so the migration and the de-plaintexting happen in one command.

The exit code is the contract.

In the default silent mode it is the only thing dndmode tells you. Every failure mode has its own number, so a wrapper script can branch on the reason without parsing anything.

Branching on it

dndmode --timer 2h
case $? in
  0) # unlocked or timed out ;;
  1) # fix the config first ;;
  4) # dismiss the sudo prompt ;;
  5) # one is already running ;;
esac

Teardown always runs

Whatever the exit code, the shutdown path is a single LIFO teardown: the shield comes down, both taps are released, the power assertion is released by its exact id, audio is restored if dndmode was the one that muted it, Focus is turned off if dndmode turned it on, and the runtime snapshot is deleted.

The only way to skip that path is kill -9 — which is exactly what the runtime snapshot exists to repair on the next launch.

Threat model

What it stops, and what it plainly does not.

dndmode is a soft-lock for cooperative environments, not red-team-grade hardware protection. Both columns below are part of the product description.

Protects against

A passerby, family member or colleague touching the keyboard or trackpad while an agent runs. Keyboard, mouse, scroll, media keys, Cmd+Tab and Cmd+Q are blocked at the HID level; trackpad gestures — Mission Control, App Exposé, Spaces swipes, the Launchpad pinch — are blocked at the session level.

Visual access to the desktop on every connected display, including probing through Mission Control, Spotlight or the Force Quit dialog.

Notification banners, hidden under the shield, and notification sounds, with the audio muted for the session — and Focus/DND optionally on top.

Leaking that keystrokes are even being observed: no feedback on a wrong code, no per-keystroke logging, no reaction in the overlay animation.

Does not protect against

Touch ID and biometric unlock — impossible to block without root.

A power-button hold (hard shutdown) and Recovery mode at boot.

Hardware keyloggers and DMA over Thunderbolt.

Malware running as root, and sustained physical access generally.

Remote SSH or VNC sessions — the target is the local console only.

A short unlock code against someone willing to sit and type. Matching is on the tail of the keystroke stream, so every keypress is a fresh attempt and there is no lockout and no rate limit. The shipped 1-step default, or a 4-step code, is minutes to hours of effort.

Limits & troubleshooting

Where it stops being convenient.

Nothing below is a bug being worked around — each one is a deliberate scope decision, and knowing it in advance is cheaper than discovering it with the shield already up.

Known limitations

No prior-Focus restore

With focus: true, dndmode turns Focus off on exit rather than restoring whatever you had before. Audio, by contrast, is restored: a session that finds audio already muted leaves it muted.

glass bleeds through

It shows a blurred desktop on purpose. Use black, matrix, terminal or dvd if you need the desktop fully hidden.

Foreground only

No daemon and no launchd mode. The terminal that launched dndmode must stay open — which is the point: the utility is meant to be observable.

One instance at a time

A second dndmode exits 5 with instructions rather than stacking a second shield on top of the first.

Needs an active display

dndmode shields the screens you can see; it does not keep a MacBook running with the lid shut. With the lid closed and no external monitor there is nothing to draw on, so startup aborts with exit 2 and no displays detected. The awake lock also does not defeat clamshell sleep — closing the lid on battery still sleeps the Mac. Run it lid-open, or in clamshell with an external display on AC power.

Signing

Recent macOS refuses unsigned binaries. make build applies ad-hoc codesigning; go install relies on Go's linker-signed signature, which launches but is not stable enough for TCC across upgrades.

Troubleshooting

Permissions lost after a go install upgrade

Each @latest rebuild changes the cdhash, which TCC uses as identity. Without a stable signature macOS sees a new app and revokes both grants.

$ make install # stable identity
# or reset and re-grant
$ tccutil reset Accessibility com.dsbasko.dndmode

Secure Event Input conflict — exit 4

Another app holds Secure Event Input: usually a Terminal sudo prompt, a password manager, or an active password field. Dismiss it and re-run. Exit 4 also fires when the tap was silently disabled and the watchdog could not bring it back.

$ ioreg -l -w 0 | grep SecureInput

Another instance is already active — exit 5

Find the pid and ask it to exit cleanly, or wait for it to finish.

$ pgrep -x dndmode
$ pkill -TERM dndmode

Cannot delete a stale runtime file — exit 7

Causes are a read-only filesystem, an ACL denying delete, or a full disk.

$ rm -f ~/.config/dndmode/runtime.json

It starts, but the code never unlocks

There is no feedback by design — a wrong code looks exactly like no input at all. Exit with Ctrl-C in the launching terminal, then check, in order: your layout (steps are physical positions); a modifier you are holding; the source reported under --debug; and then simply keep typing — there is no reset and no timeout, so a mistake costs nothing but a retype.

$ dndmode --debug
dndmode: unlock_code=ok (source=hotkey)
    ↑ not the key you edited
